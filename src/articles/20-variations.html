The Variations API lets your software work with a store's variation types, such as Size, and with the variants of each product. You can list, create, retrieve, replace, update and delete variation types, delete a single option from a type, list a product's variants, import variants into a product, and set the availability, prices, stock and order quantities of several variants at once. Each variation type has a name, a standard of text, color or image, and a list of options. All twelve endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Get every variation type, or find one by its name List variation types, page by page. Each call returns the types under variations, each with all of its options: 20 per call, or the limit you send, from 1 to 100. Send search=size to get only types whose name contains that text, in any letter case, and standard=text to get only one kind of type
Add a variation type, such as a shirt size Create a variation type with the type inside variation, such as {"variation": {"name": "Shirt Size", "standard": "text", "options": [{"label": "Small", "value": "S", "order": 1, "default": true}]}}. It returns 201 and the new type under variation, with the type's id and an id on each option. Pass the type's id as variation_id to retrieve, change or delete the type
Rename a type, or change or add options without deleting any Update a variation type with the type's id as variation_id and only what you want to change, such as {"variation": {"options": [{"id": 201, "label": "Petite"}, {"label": "Extra Large", "value": "XL", "order": 4}]}}. An option sent with the option's id changes only the fields you send for it, and an option sent without an id is added. It returns the type with every option it had and any option you added
Remove one option from a type Delete a variation option with the type's id as variation_id and the option's id as variation_option_id. It deletes the option permanently, returns 204 with no body, and leaves the type's other options as they were
Remove a variation type Delete a variation type with the type's id as variation_id and cascade=true. It deletes the type and its options permanently and returns 204 with no body
Add variants to a product, or change variants by their option labels Import a product's variants with the product's id as product_id and variations at the top level of the body, such as {"variations": [{"product_key": "Size", "variants": [{"key": "Small", "name": "Cotton T-Shirt Small", "sku": "TSHIRT-001-S", "pricing": {"base_price": 25.0}}]}]}. Create a product returns the product's id as product.id. Each group's product_key names the product's variation types, joined with /, such as Size/Colour, and each variant's key names one option label per type, joined the same way, such as Small/Red. A key the product already has changes that variant and keeps its variation_id; a new key adds a variant. It returns 201 with total_variants, the number of variants imported, and a message such as 2 of 2 variants imported successfully. It returns no variants: read them with List a product's variants. To tag the variants with a transaction number, pass transaction_no; the SDKs send it in the X-Transaction-No header
Set stock, prices, order quantities or availability on a product's variants List a product's variants with the product's id as product_id to get each variant's variation_id. Then call Update a product's variants with those values in variation_ids and the fields to set, such as {"variation_ids": [91], "available": true, "available_stock": 12}. Every variant you name gets the values you send
Find out whether a type changed without reading it Check a variation type with the type's id as variation_id. It returns headers only, with the same ETag that Retrieve a variation type returns, and the ETag changes when the type's content changes. It returns 404 when no type has that variation_id

All endpoints

These twelve endpoints list, check, create, retrieve, replace, update and delete variation types and their options at paths that start with /api/v4/admin/variations, and list, import and update a product's variants at paths that start with /api/v4/admin/products/{product_id}/variations.

Good to know

Replacing a variation type deletes every option you leave out of the body. Replace a variation type keeps only the options you send: an option sent with the option's id is changed, an option sent without an id is added, and every other option is deleted. To change or add options without deleting any, use Update a variation type, which changes only what you send.

Wrap every variation type write in variation, and send variant updates and imports with no wrapper. Create, replace and update all take {"variation": {...}}. A body without the wrapper is rejected with 400: the error's details give each top-level key the reason unknown_field, and variation the reason required. Update a product's variants is the opposite: send variation_ids and the fields to set at the top level of the body. Import a product's variants takes variations at the top level too: a body wrapped in another key is rejected with 400 and the message variations field is required.

Importing variants can add options to the store's variation types. Import a product's variants matches each product_key to the name of a variation type and each variant key to that type's option labels. A label the type does not have yet is added to the type itself, for the whole store. To add no option, use labels the type already has: List variation types returns them.

On a product whose prices include tax, the variant prices you read are net of tax. List a product's variants returns each variant's base_price and sale_price divided by the tax rate and rounded to the cent: a stored 90.99 reads 82.72. Update a product's variants stores the price you send as it is. If you write back a price you read, the stored price changes, so send the price including tax.

  • Delete a variation type with cascade=true. A type you create always has at least one option, and you cannot delete a type's last option on its own: Delete a variation option rejects it with 409 and the message a variation type must keep at least one option. Without cascade=true, Delete a variation type rejects a type that has options with 409 and the message This variation type still has N option(s). With cascade=true, the type and its options are deleted together. A type that a product's variants use cannot be deleted, even with cascade=true and even after that product is moved to the trash: the call is rejected with 409 and the message This variation type is used by N product(s).
  • An import must name the variation types the product's variants already use. When a group's product_key names other types, Import a product's variants rejects the request with 409, with a message that starts with this product's variants use the option types, and nothing is imported. A variant that sends available, is_base or tiered_pricing is rejected with 400 and the reason unknown_field. Unknown keys at the top level of the body or in a group are ignored.
  • Read imported variants back with List a product's variants. The import returns counts only. In List a product's variants, the dimensions.weight you import can read back as text, such as "4", so read it as a number or as text. No variant shows the transaction number. When you send transaction_no both in the X-Transaction-No header and beside variations in the body with different values, the header's value is stored and the body's is lost, with no error.
  • variation_ids takes each variant's variation_id, not a variation type's id. Each variant that List a product's variants returns has its own variation_id. If any entry in variation_ids is not a variant of the product whose product_id is in the path, the whole request is rejected with 400 and the message variation N does not belong to product M, and nothing is written.
  • available_stock sets stock even when inventory tracking is off. Update a product's variants writes available_stock to each variant's inventory.quantity, even when the variant's inventory tracking is off.
  • Check a variant's prices with List a product's variants, not with response=full. By default, each entry in updated has only id, which is the variant's variation_id, and name. With response=full, each entry has fourteen fields, but its sale_price and is_on_sale can differ from the values List a product's variants returns for a product on sale, and the url in each entry returns 404 if you call it. Read the variant back with List a product's variants to check its values.
  • A duplicate type name returns 409 with a body that is not valid JSON. name must be unique in any letter case. When another type already has the name you send to Create a variation type, it returns 409. The body is not valid JSON: the message is Variation type having name "<name>" already exists, with the name inserted unescaped. Check the status code instead of parsing the body.
  • A type's standard cannot change after you create it. On a replace or update, leave standard out or send the type's own value. A different value is rejected with 400, the reason read_only_field and the message cannot be changed after the variation type is created.
  • The listing returns 20 types per call unless you send limit. limit takes 1 to 100. To get more, send a higher offset, or the next page, while pagination.has_next is true. Sending both page and offset is rejected with 400 and the reason conflicting_params. The listing accepts only search, standard, limit, offset, page and field_metadata: any other query parameter, such as q or sort, is rejected with 400 and the reason unknown_parameter.
