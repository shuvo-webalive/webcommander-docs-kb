The Pages API lets your software work with a store's pages. You can list, count, create, retrieve, replace, update, duplicate and delete pages, change a page's URL and choose the store's landing page. Each page has a name, a title, a url, a layout, a visibility of open, hidden or restricted, an active flag, an access list of customers and customer groups, and password and menu settings. All fifteen endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Get every page, or only the pages that match a search List pages, page by page. Each call returns up to 20 pages under pages, most recently changed first, or up to the limit you send, from 1 to 100. Send limit=all to get every page in one call. Send search=about to get the pages whose name or title contains that text, and visibility, active or has_layout to narrow the list. Count pages takes the same filters and returns the number of matches as total
Add a page Create a page with the fields inside page, such as {"page": {"name": "About us", "title": "About us", "visibility": "open", "layout": {"id": 28}}}. name and visibility are required. When you leave out url, the store makes it from name. It returns 201 and the new page under page, with the new page's id. Pass the page's id as page_id to retrieve, change, copy or delete the page
Change a page's title, or any one field Update a page with the page's id as page_id and only the fields to change inside page, such as {"page": {"title": "About our company"}}. Every field you leave out keeps its value. It returns the page after the change
Move a page to a new URL Change the URL of a page with the page's id as page_id and {"url": "about-our-company"} at the top level of the body, not inside page. It returns the page with its new url and full_url. A url that another page already has is rejected with 409
Make a page the store's landing page Set the landing page with the page's id as page_id and no body. It returns the page with landing set to true, and the page that was the landing page gets false
Copy a page Duplicate a page with the page's id as page_id and no body, or {}. It returns 201 and the copy, with its own id, named <name> - Copy at the URL <url>-copy. The next copy is named <name> - Copy 1 at <url>-copy-1. The copy keeps the access list and the password, and has landing and menu_placement.enabled set to false
Remove a page Get the delete blockers of a page with the page's id as page_id first. It changes nothing and returns can_delete and a blockers list, each blocker with a code and a message. Then Delete a page with the same page_id. It moves the page to the trash and returns 204 with no body. Send force=true to delete the page permanently

All endpoints

These fifteen endpoints list, count, create, retrieve, replace, update, duplicate and delete the store's pages, change a page's URL, set the landing page and check whether a page can be deleted, at paths that start with /api/v4/admin/pages.

Good to know

Setting the landing page changes the landing page for the whole store. Exactly one page has landing set to true, and Set the landing page is the only call that changes it. That call changes two pages: the page you name gets landing set to true, and the page that was the landing page gets false. Before you call it, find the current landing page, the page with landing set to true in List pages with limit=all, so you can set it back. You cannot delete the landing page: Delete a page on it is rejected with 409, and Get the delete blockers of a page returns can_delete set to false and a blocker with the code landing_page and the message This page is the store landing page. Set another landing page first. Make another page the landing page first.

Send the fields inside page, except when you change a URL. Create, replace and update take {"page": {...}}. Fields sent on their own are rejected with 400 and the reason unknown_field. Change the URL of a page is the exception: it takes {"url": "..."} at the top level, rejects a body wrapped in page with 400, and rejects a request with no body with 415. Create, replace, update and the URL change all return the page inside page. Send layout as {"id": 28} with the layout's id, or null for no layout: a bare number is rejected with 400 and the reason invalid_type. id, full_url, landing, in_trash, publishing, store, author, created_at and updated_at are read-only, and a body that sends store is rejected with 400 and the reason read_only.

PUT replaces a page, and PATCH changes only the fields you send. Replace a page needs ten fields: name, title, subtitle, url, layout, visibility, body_class, active, disable_tracking and password_protection. subtitle, body_class and layout take null. Each field you leave out is named in the 400 response with the code required. To change one field, use Update a page. An update with an empty page object is rejected with 400.

A deleted page stays in the trash until you delete it with force=true. A page in the trash is left out of List pages, but Retrieve a page still returns it with in_trash set to true. Update a page on it is rejected with 409 and the reason in_trash. A second delete without force=true is rejected with 400 and the message The page could not be deleted. The page is listed in List items in the trash until you delete it permanently. After a delete with force=true, Retrieve a page returns 404 for that page_id.

  • Send If-Match to avoid overwriting someone else's change. Retrieve a page, replace, update, the URL change, setting the landing page and duplicating all return the page's ETag header. Creating a page does not, so retrieve the new page first. Send that value, quotes included, as If-Match on a replace, update or delete. If the page changed since, the call is rejected with 412 and the reason precondition_failed, and nothing is saved. Check a page returns the same ETag with headers only, so you can see whether a page changed without reading it.
  • A listing returns 20 pages per call unless you send limit. limit takes 1 to 100, or all for every page in one call. With all, pagination.limit is the total. 0 and values above 100 are rejected with 400 and the reason out_of_range. To get more, send a higher offset while pagination.has_next is true. sort takes name, title, visibility, created_at or updated_at, and order takes asc or desc. A query parameter the listing does not accept, or one you send twice, is rejected with 400.
  • A listing masks page passwords. When a page has a password, each page in List pages returns password_protection.password as ***. Retrieve a page and every write return the password as saved. To protect a page, send {"enabled": true, "password": "..."} in password_protection. Sending "enabled": false turns protection off and keeps the stored password.
  • visibility is open, hidden or restricted, but some older pages return other values. A page can return a visibility such as OPEN or public, as it was stored. Treat any value other than the three as unknown. The visibility filter on the listing matches in any letter case, so visibility=open also returns pages stored as OPEN.
  • The access list takes customer and group ids. customers takes each customer's customer_id from List customers, and customer_groups takes each group's id from List customer groups, each as a number or as {"id": ...}. visible_to takes all or selected, and you send it only with visibility set to restricted.
  • Names and URLs must be unique. A name or url that another page already has is rejected with 409, and the message names the page that has it. title and subtitle are each empty or 2 to 255 characters: 1 character or more than 255 is rejected with 400.
  • The store and not_in_store filters do not narrow the listing. store is null on every page. A store filter with a known store's id returns every page, and one that matches no store is rejected with 400 and the reason unknown_reference. not_in_store=true returns every page, and not_in_store=false returns none.
