The Products API lets your software create, read, update and delete a store's products, import a product's reviews, read and set each product's stock at each inventory location, and unassign a location from a product. Every call except Create a product takes the product's id as product_id in the path. All nine endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Find a product's product_id None of the nine Products endpoints lists products. Create a product returns the new product's id as product.id. For a product that already exists, call List stock at an inventory location with the location's id as inventory_location_id. It returns the id of each product the location holds as items[].product.id, 20 products per call. Send offset to get the next products
Add a product Create a product with the fields at the top level of the body, such as {"name": "Blue Mug", "sku": "MUG-BLUE", "base_price": 12.5}. name and base_price are required. It returns 201 and the new product under product, with status set to active and the product's id as product.id. Pass that id as product_id to the other calls. If you leave out sku, the store gives the product an sku made of PRODUCT- and 12 hexadecimal characters. An sku that another product already has is rejected with 409 and the message Product SKU already exists in another product
Read a product's prices, availability, stock and variations Retrieve a product with the product's id as product_id. It returns the product under product, or 404 with the message Product not found when no product has that product_id. Send field_metadata=true to also get a description of each field
Change some of a product's fields and keep the rest Update a product (PUT) or Patch a product (PATCH) with only the fields to change, at the top level of the body, such as {"invoice_note": "Ships in 2 business days", "advanced": {"advance_information": {"mpn": "MPN-0001"}}}. Both take the same body and change the product the same way. It returns the product after the update
Remove a product Delete a product with the product's id as product_id. It moves the product to the trash and returns 204 with no body. Retrieve a product still returns the product, with status set to trashed, and every later write to it is rejected with 409
Add reviews to a product Import a product's reviews with the product's id as product_id and the reviews inside product, such as {"product": {"reviews": [{"name": "Sam Lee", "email": "sam@example.com", "rating": 5, "review": "Great shirt", "status": "approved"}]}}. Each review needs name, email and a rating from 1 to 5. It returns 201 and every review the product has in product.reviews, oldest first, with the reviews you added last
Tag a new product, imported reviews or imported variants with a transaction number Pass transaction_no, such as IMPORT-2026-10-18, to Create a product, Import a product's reviews or Import a product's variants. The SDKs send it in the X-Transaction-No header. A new product returns the number as transaction_no, or null when you sent none
See how many units a product has at each location Retrieve a product's stock. It returns one row in locations for each location the product is assigned to, with the location's id as warehouse, its name as warehouse_name, the product's units there as stock, the low_stock_level, and is_default set to true on the product's default location. The total across the rows is available_stock
Change a product's stock at a location Retrieve a product's stock, then Set a product's stock with every row you read, changing only stock on the row you mean to change, such as {"note": "Restock", "locations": [{"warehouse": 1, "stock": 10, "low_stock_level": 2, "is_default": true}, {"warehouse": 4, "stock": 30, "low_stock_level": 5, "is_default": false}]}. When no row has is_default: true, the first row you send becomes the product's default. It returns the product's stock after the write
Stock a product at another location Set a product's stock with every row the product already has and one more row with the new location's id as warehouse. List inventory locations returns the store's locations
Stop stocking a product at a location Unassign an inventory location from a product with the product's id as product_id and the location's id, the row's warehouse, as inventory_location_id. It returns 204 with an empty body. The call is rejected with 409 while the location still holds units of the product or is its default. Before you call it, use Set a product's stock to set the location's stock to 0 and, if it is the default, send is_default: true on another row

All endpoints

These nine endpoints, at paths that start with /api/v4/admin/products, create, read, update and delete a product, import its reviews, read and set its stock at each inventory location, and unassign a location from it.

{{endpoints:products}}

Good to know

Setting a product's stock unassigns every location you leave out, even one that still holds stock. Set a product's stock replaces the product's whole set of locations with the rows you send in locations. Read the rows first with Retrieve a product's stock, send every row you want to keep, and change only the values you mean to change. You can send the rows back as you read them: warehouse_name is ignored.

Send product fields at the top level of the body, not inside product. Responses return the product inside product, but a create or PUT body wrapped in product is rejected with 400 and the message product: is not a recognised product field. A PATCH body wrapped in product is rejected with 400 in a different error shape, with code set to validation_error and the rejected fields in errors. Send the stock body's note and locations at the top level too. Import a product's reviews is the exception: wrap its reviews in product.

Deleting a product moves it to the trash. Delete a product returns 204, but Retrieve a product still returns the product, with status set to trashed. Every write to a product in the trash, including PUT, PATCH and importing reviews, is rejected with 409, and deleting it again returns 404 with the message Product already in trash. Query parameters on the delete are ignored, permanent included.

Some fields you read cannot be written. If you send the product's id, created_at, created_on, custom_class, sold_out, sold_out_label, length, width, height, weight, featured, new, model, is_draft, has_variations, urls or created_by with a value that differs from the one you read, the update is rejected with 400 and the reason read_only_field. Sending the value you read is accepted. Sending status or reviews is rejected with 400 and the reason unknown_field, so remove both before you send back a product you read. Write the dimensions in product_properties, and mpn, upc, barcode and hs_code in advanced.advance_information: a top-level mpn, upc, barcode or hs_code is rejected with 400 and the reason unknown_field. The field_metadata you get with field_metadata=true lists mpn, upc, barcode, hs_code, length, width, height, weight and sold_out_label as writable at the top level, but an update rejects each of them there.

  • PUT and PATCH both change only the fields you send, at every level. {"advanced": {"advance_information": {"mpn": "MPN-0001"}}} changes mpn and keeps the other eight fields of advance_information. A body that changes nothing, {} included, returns 200 and leaves version and the ETag header as they were.
  • Send a transaction number in the header or the body, not both. Create a product, Import a product's reviews and Import a product's variants take an optional X-Transaction-No header, which the SDKs send when you pass transaction_no. You can send transaction_no in the body instead. When you send both with different values, the header's value is stored and the body's is lost, with no error. On PUT and PATCH the header and a body transaction_no are both ignored, with 200 and no error: the product keeps the number it was created with, and the new number is not stored.
  • Importing reviews overwrites some reviews and changes some values, with no error. Import a product's reviews overwrites the review the product already has from the same email: that review keeps its id and takes the new text and rating, and the call still returns 201. A status of approved is kept, and any other value, or none, is stored as pending. title and other unknown keys are dropped. To set a review's date, send dateCreated as yyyy-MM-ddTHH:mm:ss: date, the key the response uses, is rejected with 400. Send transaction_no beside product, not inside it.
  • Setting stock changes the product too. available_stock becomes the sum of the rows' stock, and product_pricing_and_stock.low_level_stock takes the low_stock_level of the product's default location. The product's version, updated_at and last_updated_by change when its stock changes. product_pricing_and_stock.locations in Retrieve a product holds the same rows as Retrieve a product's stock.
  • The first location you assign to a product is missing from the response. On a product with no location yet, Set a product's stock returns locations: [] but stores the row. Call Retrieve a product's stock to see it. A product that already has a location returns its rows at once.
  • Retrieve a product accepts only one query parameter. Retrieve a product accepts only field_metadata, set to true, false, 1 or 0. Any other value, or any other query parameter such as limit or fields, is rejected with 400.
  • Once a location is unassigned from every product, you can delete it. After Unassign an inventory location from a product, List stock at an inventory location no longer lists the product there. Unassigning the same location again returns 404. When no product is assigned to the location, delete it with Delete an inventory location.
