The Products API lets your software list, count, create, read, update and delete a store's products, check whether a SKU is free, list special products such as the featured ones, delete several products at once, import, list, read, change and delete a product's reviews, upload, order, move and delete a product's images, read a product's SEO settings, set a product's inventory, read, set and change each product's stock at each inventory location, list a product's stock adjustments, and unassign a location from a product. Every call that works on one product takes the product's id as product_id in the path. All twenty-seven endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Find a product's product_id List products returns every product with its id. Create a product returns the new product's id as product.id. You can also call List stock at an inventory location with the location's id as inventory_location_id. It returns the id of each product the location holds as items[].product.id, 20 products per call. Send offset to get the next products
List or search the store's products List products returns the products under products, the most recently updated first, 20 per call by default and up to 100 with limit, with a pagination block. Each row is the full record Retrieve a product returns, and a product in the trash is not listed. Page with offset or page. Filter with search_text, name, sku, ids, parent (a category's id), product_type (physical, downloadable, gift_card or bundle), status (active, inactive or draft), stock, price_from and price_to, among others. Sort with sort and dir. A parameter the listing does not accept is rejected with 400
Add a product Create a product with the fields at the top level of the body, such as {"name": "Blue Mug", "sku": "MUG-BLUE", "base_price": 12.5}. name and base_price are required. It returns 201 and the new product under product, with status set to active and the product's id as product.id. Pass that id as product_id to the other calls. If you leave out sku, the store gives the product an sku made of PRODUCT- and 12 hexadecimal characters. An sku that another product already has is rejected with 409 and the message Product SKU already exists in another product
Read a product's prices, availability, stock and variations Retrieve a product with the product's id as product_id. It returns the product under product, or 404 with the message Product not found when no product has that product_id. Send field_metadata=true to also get a description of each field. The product's price is in pricing.base_price and its featured flag in advanced.product_flags.featured.enabled; flat fields such as base_price and is_featured are not returned
Change some of a product's fields and keep the rest Update a product (PUT) or Patch a product (PATCH) at the top level of the body, such as {"invoice_note": "Ships in 2 business days", "advanced": {"advance_information": {"mpn": "MPN-0001"}}}. Patch a product needs only the fields to change. Update a product must also include name, sku, base_price, product_type, available, is_on_sale, available_on_date_range, available_on_weekdays, available_for and selected_customers; a missing one is rejected with 400 and the reason required. Every other field you leave out keeps its value. It returns the product after the update
Remove a product Delete a product with the product's id as product_id. It moves the product to the trash and returns 204 with no body. Retrieve a product still returns the product, with status set to trashed, and every later write to it is rejected with 409
Add reviews to a product Import a product's reviews with the product's id as product_id and the reviews inside product, such as {"product": {"reviews": [{"name": "Sam Lee", "email": "sam@example.com", "rating": 5, "review": "Great shirt", "status": "approved"}]}}. Each review needs name, email and a rating from 1 to 5. It returns 201 and every review the product has in product.reviews, oldest first, with the reviews you added last
Tag a new product, imported reviews or imported variants with a transaction number Pass transaction_no, such as IMPORT-2026-10-18, to Create a product, Import a product's reviews or Import a product's variants. The SDKs send it in the X-Transaction-No header. A new product returns the number as transaction_no, or null when you sent none
See how many units a product has at each location Retrieve a product's stock. It returns one row in locations for each location the product is assigned to, with the location's id as warehouse, its name as warehouse_name, the product's units there as stock, the low_stock_level, and is_default set to true on the product's default location. The total across the rows is available_stock
Change a product's stock at a location Retrieve a product's stock, then Set a product's stock with every row you read, changing only stock on the row you mean to change, such as {"note": "Restock", "locations": [{"warehouse": 1, "stock": 10, "low_stock_level": 2, "is_default": true}, {"warehouse": 4, "stock": 30, "low_stock_level": 5, "is_default": false}]}. When no row has is_default: true, the first row you send becomes the product's default. It returns the product's stock after the write
Change a product's stock tracking or stock in one call Change a product's stock with the product's id as product_id and at least one of tracking, locations, note and transaction_no at the top level of the body. tracking takes enabled, available_stock and low_stock_level. It returns the product's stock and the adjustment it recorded, which is null when the stock figure did not change
See a product's stock history List a product's stock adjustments with the product's id as product_id. It returns the adjustments newest first, 20 per call unless you send limit, and offset skips adjustments. Each row has the change as delta and its note. Every row returns transaction_no as null, also for a change you sent with a transaction number
Stock a product at another location Set a product's stock with every row the product already has and one more row with the new location's id as warehouse. List inventory locations returns the store's locations
Stop stocking a product at a location Unassign an inventory location from a product with the product's id as product_id and the location's id, the row's warehouse, as inventory_location_id. It returns 204 with an empty body. The call is rejected with 409 while the location still holds units of the product or is its default. Before you call it, use Set a product's stock to set the location's stock to 0 and, if it is the default, send is_default: true on another row
Count the products that match a search Count products with the list's filters, such as search_text=shirt or status=draft. It returns total and count, which hold the same number, and does not return the products. limit, offset and sortBy are rejected with 400
Check that a SKU is free before you create or edit a product Check a product SKU with sku. It returns available set to true when no product holds the SKU. Otherwise product names the holder: its id, name and status. The check ignores letter case and also sees products in the trash and variants. Send exclude_product_id to treat the SKU of the product you are editing as free
Get the featured, new, on-sale or top-selling products List special products with type set to onSale, featured, new or topSelling. Page with max (1 to 100, default 10) and offset. For the products a customer last bought or last viewed, use lastBought or lastViewed and send customerId or customer_email
Delete several products at once Delete several products with {"ids": [102, 103]}. It moves the products to the trash and returns 200 with deleted, failed and errors. Read failed, because the call returns 200 even when some id values fail
Read a product's reviews List a product's reviews with the product's id as product_id. It returns the reviews under reviews, 20 per call, with a pagination block. Page with limit and offset. To read one review, call Retrieve a product's review with the review's id as review_id
Approve, edit or delete a review Patch a product's review with review_id and {"status": "approved", "rating": 2, "comment": "Runs small"}. status is pending or approved. Delete a product's review deletes the review permanently and returns 204
Upload images to a product Upload images to a product with one or more files as base64 text, such as {"product": {"image_and_video": {"images": [{"filename": "front.png", "base64": "..."}]}}}. To add one image, call Add an image to a product's media with {"type": "images", "filename": "side.png", "content": "..."}. Both calls take JSON, not a multipart upload, and accept images only
Delete a product's image Delete a product's image with the product's id as product_id and the image's id as image_id. It returns 204 with no body. Add an image to a product's media returns the new image's id as id, and Retrieve a product lists each image's id in media.images
Put a product's images in a new order Set the order of a product's images with the product's id as product_id and {"type": "images", "ids": [...]} at the top level of the body, naming the id of every image of the product exactly once. Any other set of id values is rejected with 400. The first id becomes the primary image, and the call returns the images in the new order under images
Move one image of a product Move a product's image with the product's id as product_id, the image's id as image_id and {"position": 1} at the top level of the body. position is the only field it takes, and the image at position 1 is primary. It returns the image as one flat row
Read a product's SEO settings Retrieve a product's SEO settings with the product's id as product_id. It returns url_handle, title, description, advanced_settings, analytics, custom_code, social and ai_visibility under seo
Set whether a product tracks stock and how many units it has Update a product's inventory with {"product": {"product_pricing_and_stock": {"track_inventory": true, "available_stock": 12, "low_level_stock": 3}}}. It returns 201. Read the result with Retrieve a product's stock. A variant keeps its own stock

Before you sync stock

A product only keeps a stock figure when its stock tracking is on. While tracking is off, the product reads available_stock: 0, a new figure is refused, and shipping an order does not lower its stock. Follow these steps:

  1. Check the product. Call Retrieve a product's stock and look at track_inventory.
  2. If tracking is on (true), set the figure with Change a product's stock: {"tracking": {"available_stock": 25}}.
  3. If tracking is off (false), turn it on and set the figure in the same call: {"tracking": {"enabled": true, "available_stock": 25}}.
If you getIt meansDo this
409 with the reason tracking_disabledYou sent a stock figure while the product's tracking is off.Send the same call again with "enabled": true inside tracking.
400 with the message locations is requiredYou used Set a product's stock on a store that keeps stock without inventory locations (locations: []).Use Change a product's stock with tracking instead.

To turn tracking off, send {"tracking": {"enabled": false}} on its own. A call that also sends a stock figure is refused with the same 409, so set the figure first and turn tracking off in a second call. Creating an order does not lower stock; creating a shipment does, for products that track it.

Good to know

Setting a product's stock unassigns every location you leave out, even one that still holds stock. Set a product's stock replaces the product's whole set of locations with the rows you send in locations. Read the rows first with Retrieve a product's stock, send every row you want to keep, and change only the values you mean to change. You can send the rows back as you read them: warehouse_name is ignored.

Send product fields at the top level of the body, not inside product. Responses return the product inside product, but a create or PUT body wrapped in product is rejected with 400 and the message product: is not a recognised product field. A PATCH body wrapped in product is rejected with 400 in a different error shape, with code set to validation_error and the rejected fields in errors. Send the stock body's note and locations at the top level too. Import a product's reviews is the exception: wrap its reviews in product.

Deleting a product moves it to the trash. Delete a product returns 204, but Retrieve a product still returns the product, with status set to trashed. Every write to a product in the trash, including PUT, PATCH and importing reviews, is rejected with 409, and deleting it again returns 404 with the message Product already in trash. Query parameters on the delete are ignored, permanent included.

Some fields cannot be written. If you send the product's id, created_at, created_on, custom_class, sold_out, sold_out_label, length, width, height, weight, featured, new, model, is_draft, has_variations, urls or created_by with a value that differs from the one you read, the update is rejected with 400 and the reason read_only_field. Sending the value you read is accepted. Sending status or reviews is rejected with 400 and the reason unknown_field, so remove both before you send back a product you read. Write the dimensions in product_properties, and mpn, upc, barcode and hs_code in advanced.advance_information: a top-level mpn, upc, barcode or hs_code is rejected with 400 and the reason unknown_field. The field_metadata you get with field_metadata=true lists mpn, upc, barcode, hs_code, length, width, height, weight and sold_out_label as writable at the top level, but an update rejects each of them there.

  • PUT must include ten fields, and both PUT and PATCH change only the fields you send, at every level. Update a product rejects a body that leaves out name, sku, base_price, product_type, available, is_on_sale, available_on_date_range, available_on_weekdays, available_for and selected_customers with 400 and the reason required. Patch a product has no required fields. {"advanced": {"advance_information": {"mpn": "MPN-0001"}}} changes mpn and keeps the other eight fields of advance_information. A body that changes nothing, {} included, returns 200 and leaves version and the ETag header as they were.
  • A product returns its prices, flags and availability inside blocks, not as flat fields. A product returns 46 fields, among them pricing, inventory, ordering, restrictions, tax, shipping, available_for_purchase, media, categories, up_sell_products, summary, description, virtual, product_url, updated_by and links, and advanced holds product_flags, product_dimension, product_identifiers and webtool. Read the base price from pricing.base_price and the featured flag from advanced.product_flags.featured.enabled: the flat fields base_price, is_featured and the others that moved into blocks are not returned. A create and a PATCH still accept the flat names, so {"base_price": 3.5} changes pricing.base_price. These block fields are read-only: product_url, links, restrictions.enabled, restrictions.display_only, restrictions.price.enabled, restrictions.purchase.enabled, shipping.enabled, the two units in advanced.product_dimension, advanced.product_flags.sold_out and advanced.webtool. A value you send in updated_by, restrictions.price.customers or restrictions.purchase.customers returns 200 and is not kept.
  • Some block fields behave differently from the flat ones. up_sell_products takes {"id": ...} records: a list of bare ids returns 200 and leaves up_sell_products empty. categories takes category ids or {"id": ...} records, and [] changes nothing. media names files the product already holds. shipping.profile (an id or {"id": ...}) is kept by an update and dropped by a create. tax.custom_tax_profile takes the id of a custom tax profile. While available_for_purchase.enabled is false, a value you write in its who_can_view, schedule or password_protection returns 200 and is not kept.
  • selected_customers and restrict_for_selected_customers are objects. Each reads {"customers": [], "groups": []} when nobody is named. To write selected_customers, send the customer ids in customers and the customer group ids in groups; a group sent as {"id": ...} is rejected with 400. restrict_for_selected_customers is read-only.
  • Send a transaction number in the header or the body, not both. Create a product, Import a product's reviews and Import a product's variants take an optional X-Transaction-No header, which the SDKs send when you pass transaction_no. You can send transaction_no in the body instead. When you send both with different values, the header's value is stored and the body's is lost, with no error. On PUT and PATCH the header and a body transaction_no are both ignored, with 200 and no error: the product keeps the number it was created with, and the new number is not stored.
  • Importing reviews overwrites some reviews and changes some values, with no error. Import a product's reviews overwrites the review the product already has from the same email: that review keeps its id and takes the new text and rating, and the call still returns 201. A status of approved is kept, and any other value, or none, is stored as pending. title and other unknown keys are dropped. To set a review's date, send dateCreated as yyyy-MM-ddTHH:mm:ss: date, the key the response uses, is rejected with 400. Send transaction_no beside product, not inside it.
  • Setting stock changes the product too. available_stock becomes the sum of the rows' stock, and product_pricing_and_stock.low_level_stock takes the low_stock_level of the product's default location. The product's version, updated_at and updated_by change when its stock changes. product_pricing_and_stock.locations in Retrieve a product holds the same rows as Retrieve a product's stock.
  • The first location you assign to a product is missing from the response. On a product with no location yet, Set a product's stock returns locations: [] but stores the row. Call Retrieve a product's stock to see it. A product that already has a location returns its rows at once.
  • Retrieve a product accepts only one query parameter. Retrieve a product accepts only field_metadata, set to true, false, 1 or 0. Any other value, or any other query parameter such as limit or fields, is rejected with 400.
  • Once a location is unassigned from every product, you can delete it. After Unassign an inventory location from a product, List stock at an inventory location no longer lists the product there. Unassigning the same location again returns 404. When no product is assigned to the location, delete it with Delete an inventory location.
  • Upload images as JSON with the file base64-encoded. Upload images to a product and Add an image to a product's media reject a multipart body with 415 and the message Content-Type must be application/json. Send the file's bytes as base64 text. Only images are accepted: a type of videos or specification_file is rejected with 400 and the reason not_supported. The store keeps the file under your filename with a UUID and _ in front, such as <uuid>_front.png, so compare the end of the name.
  • The two upload calls take different bodies and return different shapes. Upload images to a product takes one or more files inside product.image_and_video.images and returns 201 with only the files it just stored in product.images, and no Location header. Add an image to a product's media takes one file at the top level of the body, with content as base64 text or a data:image/png;base64,... address and an optional position. It returns 201 with a Location header and the image as one flat row: id, filename, position, primary, alt_text, url and thumbnail_url. A field named base64 on that call is rejected with 400 and the reason unknown_field. Deleting an image twice returns 404 the second time.
  • Delete several products moves them to the trash and returns 200 even when some fail. Send {"ids": [...]} to Delete several products: product_ids and an empty list are rejected with 400. deleted counts the products moved to the trash, failed counts the others, and errors lists each failure with its id and a reason such as not_found. A product in the trash still holds its SKU, which Check a product SKU reports with status set to trashed, and Count products and List products do not include it.
  • Count products takes the list's filters, but not its paging or sorting. limit, offset and sortBy are rejected with 400 and the reason unknown_parameter. status takes active, inactive or draft, and product_type takes physical, downloadable, gift_card or bundle; any other value is rejected with 400 and the reason invalid_enum. category is accepted and filters nothing. A count or a list without status includes draft products.
  • List special products needs type, and two types need a customer. type must be onSale, featured, new, topSelling, lastBought or lastViewed, in that letter case. lastBought and lastViewed are per customer: send customerId (the customer's customer_id or internal_id) or customer_email. customer_id is not read, and a customerId that no customer has is rejected with 400 and the reason unknown_reference. A per-customer selection with no products also returns "status": "success".
  • A review's status is pending or approved, and the review list pages. Patch a product's review rejects a status of rejected with 400 and the reason invalid_enum. List a product's reviews takes limit (1 to 100, default 20) and offset, and ignores status and page: a list sent with status=pending still returns approved reviews. Retrieve a product's review returns 404 with the message Review not found when no review has that review_id, and 400 when the review belongs to another product.
  • Updating a product's inventory sets the stock figure, and a variant keeps its own. Update a product's inventory takes track_inventory, available_stock and low_level_stock inside product.product_pricing_and_stock and returns 201. The stock of the product's variants does not change. The call takes the optional X-Transaction-No header, which the SDKs send when you pass transaction_no: the number is stored when the product has none, but the response to that first write shows the earlier value, null.
