The Common settings API lets your software read and change a store's settings by group and key, and read the fields of the customer registration form. Settings come in groups, such as general, locale, email, e_commerce, notifications and customer_registration_field. In every group except notifications, a setting has a config_key and a value. The paths start with /api/v4/settings and /api/v4/create-customer-fields, directly under /api/v4 and not under /api/v4/admin. All six endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Read every setting in one group Get settings with the group's name as type, such as type=general. It returns settings, with the group as a list of config_key and value pairs
Read one setting Get settings with type and the setting's key as config_key, such as type=customer_registration_field&config_key=abn_placeholder. It returns {"settings": {"customer_registration_field": [{"config_key": "abn_placeholder", "value": "Enter your ABN"}]}}
Change one or more settings Update settings with the groups to change inside settings, such as {"settings": {"customer_registration_field": [{"config_key": "abn_placeholder", "value": "Enter your ABN"}]}}. Only the keys you send change. It returns 200 and every settings group of the store, about 2 MB
Change settings with POST instead of PUT Save settings takes the same body as Update settings and saves it the same way. In either call, each group can be a list of config_key and value pairs or an object of config_key to value, such as {"settings": {"customer_registration_field": {"abn_placeholder": "Enter your ABN"}}}. It returns 201 instead of 200, with every settings group of the store
See which fields the customer registration form shows Get the customer registration fields, with no query parameters. It returns fields, the keys of the active fields in their order, such as first_name, and fields_configs, six settings for each of the 20 fields, inactive ones included: _order, _key, _label, _placeholder, _active and _required, such as first_name_label
Change a field on the customer registration form Update settings in the customer_registration_field group, such as the key abn_placeholder. The form follows that group
Check that a settings group can be read, without getting its body Check settings with the group's name as type, such as type=general. It returns 200 with headers only, or 404 when no group has that name

All endpoints

These six endpoints read, check and change the store's settings at /api/v4/settings, and read and check the customer registration form at /api/v4/create-customer-fields.

Good to know

A write changes settings for the whole store, and one entry that is not valid saves nothing. Update settings and Save settings change only the keys you send, but one entry that is not valid rejects the whole request with 400. A group the store does not have is rejected with the detail code unknown_group, and a key the group does not have with unknown_key. Send the groups inside settings: groups sent without it are each rejected as unknown_field, with settings as required. A body of {} is rejected with the message request body is empty.

A write can take longer than the SDKs' default timeout. A write returns every settings group of the store, about 2 MB, and can take from 5 to more than 50 seconds. The SDKs' default timeout is 30 seconds, so build the client with a longer timeout, such as 120 seconds. If Save settings times out, read the keys back with Get settings before you send it again.

Send type on every read. Without it, Get settings returns every group, about 2 MB, and can take 30 seconds or more. An empty type= counts as no type. type takes one group: an unknown group, or a comma list of groups such as general,locale, is rejected with 404 and the detail code unknown_type. For an unknown group, the message is Unknown settings type: <type>.

Never send a *** value back. Passwords, keys and tokens read as ***, not as the stored value. This includes smtp_password in the email group, and the password_* and retype_password_* keys in customer_registration_field. Write only the keys you change, so a *** you read never goes back to the store.

  • Read one key per call with config_key. A comma list such as abn_label,abn_placeholder matches nothing and returns {"settings": {}} with 200. Send one call per key, or read the whole group with type alone. Without type, the response places the key under the group it belongs to.
  • Every value is text, except in the notifications group. Values come back as strings, such as "true" or "18", and a number you write is stored as its text: 5 becomes "5". The notifications group is an object of names to true or false, such as {"order_emails_enabled": true, "customer_emails_enabled": true}, not a list.
  • The registration form returns booleans where Get settings returns text. Get the customer registration fields returns each field's _active and _required as true or false. Reading the same keys from the customer_registration_field group returns them as text, such as "true". _order is text in both.
  • Get settings takes only type and config_key, each once. Any other query parameter, limit and offset included, is rejected with 400 and the message unknown query parameter(s): <name>. Sending type or config_key twice is rejected with 400 and the message Send each query parameter once: <name>. The response is not paginated. Get the customer registration fields takes no query parameters at all.
  • /settings accepts GET, HEAD, PUT and POST, and /create-customer-fields accepts only GET and HEAD. Neither path sends an ETag header.
