The Trash API lets your software work with a store's trash. A category, customer, blog post or page that you delete through its own resource stays in the trash until you restore it or delete it permanently. With this API you list the items in the trash and the types it holds, and you restore items or delete them permanently, one at a time or up to 100 per call. All eight endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
See which categories, products or blog posts are in the trash List items in the trash with type, such as type=Category, or several types separated by commas, such as type=Product,Category. It returns the items under items, newest first, 20 per call unless you send limit. Each item has its id, type, name and updated, the time it was moved to the trash. Send a higher offset or the next page while pagination.has_next is true
Find a trashed item by its name List items in the trash with type and search, such as type=Category&search=spring. It returns the items whose name contains that text. Send removed_from and removed_to, as yyyy-MM-dd dates, to keep only items trashed in that range
Find out which types the trash holds List trash types, with no query parameters. It returns the twelve types under types, in alphabetical order, each as an object with a type field, such as {"type": "BlogPost"}
Put a category, customer or blog post in the trash Delete it through its own resource: Delete a category, Delete a customer or Delete a blog post. The item then stays in the trash until you restore it or delete it permanently
Restore one item Restore an item from the trash with the item's type as trash_type and the id the item has in its own resource as trash_item_id: a category's id, or a customer's customer_id. Send no body. It returns 201 with status set to success and a message such as Category restored successfully, not the item. Read the item from its own resource to get its fields
Delete one item permanently Delete an item permanently with the item's type as trash_type and the id the item has in its own resource as trash_item_id. It returns 204 with no body. You cannot restore the item afterwards
Restore or delete many items in one call Restore items in bulk or Delete items permanently in bulk with 1 to 100 items, such as {"items": [{"type": "Category", "id": 1234}, {"type": "BlogPost", "id": 99}]}. It returns the number of items restored in restored, or deleted in deleted, the number that failed in failed, and one entry in errors for each item that failed

All endpoints

These eight endpoints list the items in the trash and the types it holds, return the headers of each list, and restore items or delete them permanently, one at a time or in bulk, at paths that start with /api/v4/admin/trash.

Good to know

Send a type other than Customer on every listing call. Without type, or with type=Customer, List items in the trash can take about 90 to 110 seconds to return a page. Check the trash list runs the same query and takes as long. With type=Category, type=Product or type=BlogPost, a page returns in about a second. If you must list customers, set your client's request timeout above 110 seconds.

You name an item by its type and the id it has in its own resource. The trash has no ids of its own. Pass a category's id, or a customer's customer_id, as trash_item_id in a path, or as id in a bulk item. The same number is the item's id in List items in the trash.

Send BlogPost, not blog_post. trash_type and the type of a bulk item take a value from List trash types, in any letter case: Category, category and CATEGORY all work. A two-word type has no snake_case form: blog_post is rejected with 400 and the message unknown trash type 'blog_post'. Listed items and errors entries return the type in PascalCase, whatever case you sent.

Only an item in the trash can be restored or deleted permanently. An item that is not in the trash is rejected with 409 and the message <Type> with id <id> is not in trash. To delete a live item permanently, delete it through its own resource first. After a permanent delete the item is gone: a restore, a second delete and the item's own resource all return 404.

A bulk call returns 201 even when some items fail. Restore items in bulk and Delete items permanently in bulk return 201 when at least one item succeeds, and 400 with the same body when every item fails. Check failed and errors in every response. Each failed item has an errors entry with its type, its id and a reason, such as Category with id 1234 is not in trash. An item you list twice is restored or deleted once, and the second copy fails.

  • A bulk body takes only type and id in each item. Send items at the top level of the body. A missing or empty items, more than 100 items, an item with any other field, or an item whose type is not a trash type is rejected with 400, and nothing is restored or deleted.
  • A listing returns 20 items per call unless you send limit. A limit above 100 returns 100 items, and pagination.limit shows 100. Send limit once: sending it twice, such as limit=2&limit=3, returns 500. A query parameter the listing does not accept, such as q, is rejected with 400.
  • Send order in lower case. order=DESC is accepted but sorts in ascending order. Send order=desc instead. sort takes name, type, updated or removed_at, which sorts by updated.
  • An item's updated time is in UTC, with no time zone designator. It is the time the item was moved to the trash, such as 2026-10-18T11:16:07.
  • The item path accepts only DELETE and OPTIONS. GET on /api/v4/admin/trash/{trash_type}/{trash_item_id} returns 405.
  • Many writes in a row can be rejected with 429. The error code is rate_limited, and the Retry-After header gives the seconds to wait before you retry.
