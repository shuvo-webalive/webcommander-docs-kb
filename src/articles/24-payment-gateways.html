The Payment gateways API lets your software read and change your store's checkout payment gateways. You can list and count the gateways, retrieve one gateway with its own settings, and change a gateway's fields with PUT or PATCH. You cannot create or delete a gateway: the gateways already exist in your store. Each gateway has an id, a fixed code such as CHQ, a name, added, enabled, default and promotional flags, a zone, an information text, a visibility rule for who sees it at checkout, the delivery types it is offered for in allowed_for, a surcharge, its messages and its settings. All eight endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Get every payment gateway List payment gateways, page by page. Each call returns up to 20 gateways under payment_gateways, or up to the limit you send, from 1 to 100, in ascending order of the gateway's id. To get the next page, raise offset by limit while pagination.has_next is true. Listing rows have no settings
Find gateways by name, or count the matches List payment gateways with search, such as search=card. It returns the gateways whose name contains that text, in any letter case. Send exclude with a comma-separated list of gateway code values, such as exclude=PIS,CHQ, to leave those gateways out, and promotional or added to filter on those fields. Count payment gateways takes the same search, exclude, promotional and added and returns the number of matches as total
Read a gateway's settings Retrieve a payment gateway with the gateway's id as payment_gateway_id. It returns the gateway under payment_gateway, with the fields a listing row has plus settings. Each gateway returns its own settings fields. Offline gateways return {}, and a stored secret, such as an API key, reads ********
Change a gateway's information text Update a payment gateway with the gateway's id as payment_gateway_id and {"information": "Make cheques payable to Example Store."}. information takes at most 2000 characters, and "information": null clears it. It returns the whole gateway after the change under payment_gateway, with settings
Stop offering a gateway for store pickup Update a payment gateway with the gateway's id as payment_gateway_id and {"allowed_for": {"store_pickup": false}}. allowed_for merges key by key, so shipping and delivery keep their values
Choose which customers or customer groups see a gateway at checkout Update a payment gateway with the gateway's id as payment_gateway_id and a visibility object whose type is selected. Send customers as a list of customer id values from List customers, and customer_groups as a list of customer group id values from List customer groups. The response returns each selected customer and customer group as an id and name pair
Find out whether a gateway exists Check a payment gateway with the gateway's id as payment_gateway_id. It returns 200 with headers only when a listed gateway has that id, and 404 when none does

All endpoints

These eight endpoints list, count, retrieve and update the store's payment gateways, and return the headers of each, at paths that start with /api/v4/admin/payment_gateways.

{{endpoints:payment_gateways}}

Good to know

You cannot send a retrieved gateway back unchanged. A PUT or PATCH that sends the gateway as Retrieve a payment gateway returns it is rejected with 400. code and promotional are read-only, and sending either one, even unchanged, is rejected. "surcharge": null is rejected with the message must be an object. Send only the fields you want to change.

Send the fields at the top level of the body, not inside payment_gateway. Update a payment gateway with PUT and Update a payment gateway both take the gateway's fields directly in the body, such as {"allowed_for": {"store_pickup": false}}. A body wrapped in payment_gateway, or any field that is not a gateway field, is rejected with 400, the reason unknown_field and the message is not a payment gateway field. The responses return the gateway inside payment_gateway.

PUT and PATCH both change only the fields you send. Update a payment gateway with PUT does not replace the gateway: a field you leave out keeps its value, as it does with Update a payment gateway. allowed_for merges key by key on both. An empty body {} is rejected with 400 and the message request body is empty.

Pass the gateway's id as payment_gateway_id, not its code. Read the gateway's id from List payment gateways. A gateway's code in the path, such as CHQ, returns 404 with the reason not_found and the message Payment gateway <payment_gateway_id> was not found. Codes go in the exclude parameter of the listing and the count.

  • You cannot create or delete a gateway. POST and DELETE on a gateway, POST and PUT on the list, and PATCH on /count are rejected with 405 and the reason method_not_allowed. OPTIONS returns 204 with an Allow header: GET, HEAD, OPTIONS on the list and on /count, and GET, HEAD, PUT, PATCH, OPTIONS on a gateway.
  • A listing returns 20 gateways per call unless you send limit. limit takes 1 to 100. 0 or a value above 100 is rejected with 400 and the reason out_of_range. A limit that is text, such as all, or an offset that is negative or not a number, is rejected with 400 and the reason invalid_integer. A page past the end returns no gateways, and its pagination.has_previous is false even though offset is above 0. Stop when pagination.has_next is false.
  • enabled and code do not filter the listing. List payment gateways ignores sort, order, dir, enabled, code, q, field_metadata and any other parameter it does not know, and always lists gateways in ascending id order. The filters that work are search, exclude, promotional and added.
  • Only a single-gateway read or a write returns settings. Listing rows have no settings, so use Retrieve a payment gateway to read them. The fields in settings differ for each gateway, offline gateways return {}, and a stored secret, such as an API key or a client secret, reads ********.
  • Writes check information and zone. An information text longer than 2000 characters is rejected with 400 and the reason too_long. zone takes a zone's id or {"id": ...}, and an id that no zone has is rejected with 400, the reason unknown_reference and the message no zone exists with id <id>.
  • Errors have one shape. The body is an error object with code, message, details and request_id. Each details entry names the rejected field and gives its code and message. The entry's message is null when limit or offset is not a valid integer or limit is 0; read the top-level message instead. A read-only field such as code gets two entries, with the reasons read_only and unknown_field.
  • No response has an ETag header.
