The Blog categories API lets your software work with the categories a store files its blog posts under. You can list, create, retrieve, update and delete blog categories, and give each one a name, a URL slug, a description and an image. When you create a category, you can also file existing blog posts under it. All five endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Get every blog category, or find out how many there are List blog categories, page by page. Each call returns at most 20 categories under blog_categories, and pagination.total is the number of categories across all pages
Add a blog category, such as "Recipes" Create a blog category with {"blog_category": {"name": "Recipes"}}. It returns 201 and the new category under blog_category, with the category's id. Pass that id as blog_category_id to retrieve, update or delete the category
Add a category with an image, or replace a category's image Create a blog category with an image. Put the file in its base64, base64-encoded and without a data: prefix, and add file_name, title and alternative_text. The response's image.link points to the store's copy of the file. To replace the image, send a new base64 to Update a blog category, with the category's name and current description
File existing blog posts under a new category Create a blog category with blogs, a list of entries that each hold a blog post's id, such as [{"id": 1234}]. Each post then lists the category in its categories
Rename a category or change its description Retrieve a blog category to read its current name and description, then Update a blog category with both, even the one you do not change. A description you leave out is saved as "". A new name does not change the category's url: send a new url to change it
Check that a category exists Retrieve a blog category with the category's id as blog_category_id. It returns 404 when no blog category has that blog_category_id. Do not use HEAD: it returns 404 even for a category that exists
Remove a category Delete a blog category with the category's id as blog_category_id. It returns 204 with no body. The category's uploaded image is deleted with it, and its blog posts are kept. Rarely, Retrieve a blog category still returns the category with 200 straight after the delete. To confirm the delete, delete the category again: it returns 404 once the category is gone

All endpoints

These five endpoints list, create, retrieve, update and delete the store's blog categories, at paths that start with /api/v4/admin/blog_categories.

{{endpoints:blog_categories}}

Good to know

Updating a blog category clears its description unless you send it again. A description you leave out of an update, or send as null, is saved as "". If you leave out url, image or blogs, the category keeps what it has. name is required on every update, even when it does not change. To keep the description, send it with every call to Update a blog category, as in {"blog_category": {"name": "Seasonal Offers", "url": "seasonal-offers", "description": "Offers and clearance announcements."}}. PATCH is rejected with 405 and the code method_not_allowed, so send every change with PUT.

Wrap the category's fields in blog_category when you create or update it. Send {"blog_category": {"name": "Recipes"}} to create a category. A body that sends the fields without the wrapper, wraps them in the plural blog_categories, or is {} or {"blog_category": {}}, is rejected with 400 and the message blog_category info missing. Create, retrieve and update return the category inside blog_category too. Leave out the category's id, which the store assigns and the retrieve, update and delete calls take as blog_category_id. A create with an id inside blog_category returns 500 and stores nothing, and an update ignores it. Create and update ignore seo_configs, so you cannot set a category's SEO entries through the API.

After a rejected limit, offset, page, sort or dir, your next request on the same client returns the same 400. It does so even when its own parameters are valid, and the error has a new request_id. The request after that runs normally, and so does every request on a new client. When a request with valid parameters gets that repeated 400, send it again.

  • name must be unique, and a create without url makes one from name. name is required on create and update, and must be 2 to 255 characters. A name another category already has is rejected with 400, not 409, and the message Blog category name exists. Whether the store makes the url from name or you send one, the store lowercases it, turns each run of characters other than ASCII letters, digits and _ into one hyphen, drops a hyphen at either end and cuts it to 50 characters. A url another category already has is saved with -1 added to the end, so read url from the response.
  • An image is stored only when you send base64. image takes file_name, base64, title and alternative_text. Send base64 without a data: prefix: a value such as data:image/png;base64,... is rejected with 400 and the message Image upload operation failed. Please upload a valid Image. Without base64, the store ignores the other image fields, so to change title or alternative_text, upload the image again. A category without an image returns image as {}. image.link ends in a query string that changes on every read, so compare links without it. Deleting the category deletes the uploaded file, and its image.link then returns 404.
  • File blog posts under a category with blogs; the category's responses never list them. On a create, send blogs as a list of entries that each hold a blog post's id, such as [{"id": 1234}]. Each of those posts then lists the category in its categories. An update without blogs, or with [], keeps every blog post filed under the category. Deleting a category keeps its blog posts and takes the category off their categories.
  • A listing returns at most 20 categories per call, ordered by name. The default order ignores letter case. A larger limit is capped at 20. To get more, send the next page or a higher offset while pagination.has_next is true. To change the order, send sort with the category field to sort by: id, name, url, description, created or updated. Any other sort, including created_on and last_updated_on, is rejected with 400 and the message Sort field not exist. Send dir as asc or desc, in lower case: the store ignores a capitalised value such as DESC and returns the categories in ascending order. Only limit, offset, page, sort, dir and field_metadata are accepted: any other parameter, such as q, search or name, is rejected with 400. There is no count endpoint: GET /api/v4/admin/blog_categories/count is rejected with 400 and the message id must be a number, so read pagination.total instead.
