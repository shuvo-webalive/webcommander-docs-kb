The Blogs API lets your software work with a store's blog posts and the comments on them. You can list, count, create, retrieve, replace, update and delete blog posts, and add, list, retrieve, approve and mark as spam the comments on each post. All twelve endpoints are available in all seven WebCommander SDKs.

Common tasks

You want to Use
Get every blog post, or only the posts in one blog category or with one visibility List blog posts, page by page. Each call returns at most 20 posts under blogs, latest date first. To get only the posts in one blog category, send category set to the blog category's id. To get only the posts with one visibility, send visibility as open, hidden or restricted. For the number of posts alone, use Count blog posts: it returns the number as blogs.count and takes the same ids, category and visibility filters
Publish a new blog post Create a blog post with the post's fields inside blog. Only title is required. Put the post's body in content. To publish the post, send is_published set to true: if you leave it out, it is set to false. To file the post under blog categories, send categories as a list of objects that each hold a blog category's id, such as [{"id": 31}]. The store makes the post's url from title and ignores a url you send. It returns 201 and the new post under blog. Pass the post's id as blog_id to the other calls
Change a post's title, or any other field, and keep the rest as it is Update a blog post with the post's id as blog_id and only the fields you change, such as {"blog": {"title": "Spring Sale: Final Week"}}. It returns the post after the change. A new title leaves url as it was. To change url, send the new url beside title: a url sent without title is ignored
Show a post only to chosen customers or customer groups Update a blog post with the post's id as blog_id, visibility set to restricted, visible_to set to selected, and selected_customers such as {"customers": [5501], "groups": []}. Put each customer's internal_id from List customers in customers, and each customer group's id in groups. It returns the post, where each customer in selected_customers appears as the customer's internal_id and name
Add a comment to a post Add a comment to a blog post with the post's id as blog_id. Put content, and optionally name and email, inside blog and then comment, as in {"blog": {"comment": {...}}}. It returns 201 and the comment under comment, with status set to pending. Leave status out of the body: the store saves any status you send without checking it
Approve a comment, or mark it as spam List comments on a blog post with the post's id as blog_id. It returns every comment on the post, oldest first, in one response. Pass a comment's id from comments[].id as blog_comment_id to Approve a comment or Mark a comment as spam. Each returns 201 and the comment with its new status
Remove a blog post Delete a blog post with the post's id as blog_id. It moves the post to the trash and returns 204 with no body. No call on this API restores the post, and no create or replace can use its title again

All endpoints

These twelve endpoints list, count, create, retrieve, replace, update and delete blog posts, and add, list, retrieve, approve and mark as spam the comments on each post, at paths that start with /api/v4/admin/blogs.

Good to know

Replacing a blog post resets the fields you leave out of the body. Replace a blog post sends PUT, and needs title and visibility every time. Most fields you leave out are reset: it sets content to null, is_published to false, date to the current time, categories to the store's default category, seo_configs to {"meta_tag": []}, visible_to to null and selected_customers to []. It keeps the image and created_by, and keeps url unless you send a new one. To change only some fields, use Update a blog post, which sends PATCH.

Wrap every request body in blog, comments included. Send {"blog": {...}} to create, replace or update a blog post, and {"blog": {"comment": {...}}} to add a comment. A blog post write without the wrapper, or with an empty one, is rejected with 400 and the message blog info missing. In a blog post write, a field the store does not recognise is rejected with 400 and the reason unknown_field; in a comment, the store drops it. A comment that is not wrapped in both returns 404, not 400, with the message comment is required. Leave the post's id out of the body: the store assigns it, and a create that sends an id field inside blog returns 500 and stores nothing. Send each blog category in categories as an object holding the category's id, such as [{"id": 31}]: a bare number, such as [31], returns 500.

Deleting a blog post moves it to the trash, and no call on this API restores it or empties the trash. The post leaves the listing and the count, and retrieving, replacing or updating it returns 404. Deleting it again returns 404 with the message Blog already in trash. Its title stays taken: a create or replace with that title, in any letter case, is rejected with 400, and the message says the title is already used by a blog in the trash; restore or rename it. Its comments stay readable and you can still approve them, but adding a comment to the post returns 404.

In every comment response, the top-level id is the blog post's id, not the comment's. Adding, retrieving, approving or marking a comment as spam returns {"id": <blog_id>, "comment": {...}}, and the comment listing returns {"id": <blog_id>, "comments": [...]}. Read the comment's own id from comment.id, or from comments[].id in the listing, and pass it as blog_comment_id. No call updates or deletes a comment.

After the listing rejects limit=0, a sort or a dir, your next request on the same client returns the same 400. It does so even when its own parameters are valid. The request after that runs normally, and so does every request on a new client. When a request with valid parameters gets that repeated 400, send it again.

  • A listing returns at most 20 blog posts per call, latest date first. A larger limit is capped at 20. To get more, send the next page or a higher offset while pagination.has_next is true. To change the order, send sort as id, name, url, date, created or updated, and dir as asc or desc. Any other sort, including title, is rejected with 400 and the message Sort field not exist, and any other dir with the message Sort order must be asc or desc. Only limit, offset, page, sort, dir, ids, category, visibility, search and field_metadata are accepted: any other parameter is rejected with 400. search is accepted but filters nothing: the listing returns the same posts whatever you send.
  • Repeat ids for each blog post you want. To list or count several posts, send each post's id in its own ids, as in ids=1201&ids=1202. A comma list such as ids=1201,1202 returns 500, and the listing rejects a bracketed name such as ids[]=1201 with 400.
  • A restricted blog post names its audience by each customer's internal_id. Set visibility to restricted and visible_to to selected, and send selected_customers as {"customers": [...], "groups": [...]}, with each customer's internal_id from List customers and each customer group's id. A customer's customer_id sent there is dropped without an error, which leaves the audience empty. A post returns selected_customers as an object once it names anyone, and as [], a list, while it names no one.
  • Check that a blog post exists with Retrieve a blog post. Pass the post's id as blog_id. It returns 404 and the message Blog not found when no blog post has that blog_id, or when the post is in the trash. HEAD on the same path returns 404 even for a post that exists.
  • A cover image changes only when you send base64. To upload one when you create, replace or update a blog post, send image inside blog, with the file, base64-encoded, in base64, and the image's file_name, title and alternative_text. A new base64 replaces the current image. An image sent as {} or null, or with a new image title and no base64, leaves the image as it is. No call removes an image. image.link ends in a query string that changes on every read, so compare links without it.
  • Approving a comment does not clear its spam flag. A comment marked as spam and then approved has status set to approved and spam still set to true.
