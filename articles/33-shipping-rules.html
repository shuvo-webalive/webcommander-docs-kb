The Shipping rules API lets your software work with a store's shipping rules. A shipping rule has a name and joins a shipping class, a shipping rate and the zones they apply to, and a shipping profile groups rules. You can list, count, create, retrieve, replace, update and delete rules. All ten endpoints are available in all seven WebCommander SDKs.

Common tasks

Get every rule, or only some List shipping rules, page by page. Each call returns up to 20 rules under shipping_rules, newest first, or up to the limit you send, from 1 to 100. Send search=metro to get the rules whose name contains that text, zone_id or shipping_class_id to get the rules that have that zone or class, and method or handling_cost to match the rule's shipping rate. Count shipping rules takes the same filters and returns the number of matches as total
Add a rule Create a shipping rule with the fields inside shipping_rule, such as {"shipping_rule": {"name": "Metro", "shipping_class": 2, "shipping_rate": 21, "zones": [5]}}. Only name is required. It returns 201 and the new rule, with its id. Pass that id as shipping_rule_id to retrieve, change or delete the rule
Put a new rule on a shipping profile Create a shipping rule with profile_id set to the id of the profile
Change the zones, class or rate of a rule Update a shipping rule with the rule's id as shipping_rule_id and only the fields to change inside shipping_rule, such as {"shipping_rule": {"zones": [5, 6]}}. zones is the full new list. A shipping_rate or shipping_class of null takes it off the rule. To replace the whole rule, use Replace a shipping rule
Remove a rule Delete a shipping rule with the rule's id as shipping_rule_id. It returns 204 with no body. The rule's shipping rate and zones stay. A rule that is on a shipping profile is rejected with 409

Good to know

A rule that is on a shipping profile cannot be deleted. Delete a shipping rule on it is rejected with 409, the code in_use and the id of the profile. The profiles list on the rule shows which profiles use it. Take the rule off those profiles first. Deleting a rule keeps its shipping rate and its zones.

Send the fields inside shipping_rule. Create, replace and update take {"shipping_rule": {...}}. A body without the wrapper is rejected with 400, and so is a field the rule does not have or an id in the body. Responses return the rule inside shipping_rule.

  • Send a class, a rate or a zone by its id. shipping_class and shipping_rate take an id, bare as 2 or as {"id": 2}, or null. zones takes the whole list of zone id values, bare or as {"id": ...}, each zone once. An unknown id, 0, a decimal such as 1.5, text or a repeated zone is rejected with 400. A class, rate or zone you leave out reads null, null and [].
  • PUT replaces a rule, and PATCH changes only the fields you send. Replace a shipping rule needs name, description, shipping_class, shipping_rate and zones. description, shipping_class and shipping_rate take null, and zones takes []. Each field you leave out is named in the 400 response with the code required.
  • Rule names are unique, in any letter case. A name that another rule has is rejected with 409 and the code duplicate. Send suggest_name as true on a create to get the next free name, such as Metro(1), instead.
  • A filter with an id that no record has is rejected. A zone_id or shipping_class_id that no zone or class has is rejected with 400 and the code invalid_reference. A rule that matches several zones is listed once.
  • You can file a rule under a transaction number. Send transaction_no inside shipping_rule, or the X-Transaction-No header on a create. When you send both, the header wins.
  • A listing returns 20 rules per call unless you send limit. limit takes 1 to 100: 0, a value above 100 and a value that is not a number, such as all, are rejected with 400. To get more, send a higher offset while pagination.has_next is true. sort takes id, name, description, created_at, updated_at or transaction_no, and order takes asc or desc.
