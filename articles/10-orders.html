The Orders API lets your software work with a store's orders. You can list, count, create, change, cancel and delete orders, move an order to another status, add comments, record payments, refunds and shipments, and email invoices. All twenty-four endpoints are available in all seven WebCommander SDKs.

Common tasks

Find the orders that are in progress and not yet paid List orders with order_status set to in_progress and payment_status set to unpaid. Each call returns at most 20 orders, newest first. Send page or offset to get the next orders
Create an order for a customer Create an order with the customer's customer_id and a products list, each line with a product_id and a quantity. Send the fields at the top level of the body, not inside order. The new order is in_progress and unpaid, and the response returns it with its order_id
Record a payment the customer made Record a payment on an order with the payment wrapped in payment, including its payment_method, which is required. It returns a receipt whose id is the payment_id that Refund a payment takes. To create the order and record a payment in one call, use Create an order with a payment, which records the payment with payment_method set to API, whatever you send
Ship some or all of an order's lines Create a shipment with method, shipping_date and shipment_items. In shipment_items, send each order line's item_id as order_item_id, with the quantity to ship. The response returns the new shipment with its shipping_id. Retrieve an order's shipment status then returns shipment_status as partial while some units are still to ship, or shipped once every unit has shipped
Give a customer money back from a payment Refund a payment with the payment's payment_id, an Idempotency-Key header, and the amount wrapped in refund, such as "5.00". The order's paid goes down and its refunded goes up
Complete, pause or cancel an order Change an order's status with status set to completed, paused or cancelled. This call does not read the key order_status. It returns the order with its new order_status. To cancel, you can also use Cancel an order, which needs no body
Email an order's invoice Send an order's invoice with the order's internal_id as order_internal_id, not its order_id. The invoice goes to the email address of the order's billing address, and the response names that address in sent_to

Good to know

Two paths take the order's internal_id, not its order_id. Retrieve an order's custom fields and Send an order's invoice find the order by its internal_id, which you pass as order_internal_id. If you pass the order's order_id instead, they return 404, unless another order has that number as its internal_id: then they return that other order's custom fields or email that other order's invoice. Every other order path takes the order's order_id. Every response that returns an order includes both numbers, so read internal_id from it before you call either path. Two responses name the numbers differently. In the response to Retrieve an order's custom fields, order_id holds the internal_id you passed. In the response to Refund a payment, order_id holds the order's internal_id and order_no holds its order_id.

An order comes back in one of two shapes. Retrieve an order, List orders, Update an order and Update selected order fields return the order in sections: customer, billing_address, shipping_address, items, shipping, discounts, charges_totals, payments and fulfillment. Create an order, Create an order with a payment, Cancel an order, Change an order's status and List a customer's orders return it flat. In the flat shape, the totals and fulfillment fields are at the top level, the customer is in customer_summary and the lines are in order_line_details. Before the first shipment, the flat shape shows shipping_status as unshipped, and the sectioned shape shows not_shipped. An order in a List orders response has no billing_address or shipping_address, and its customer has only customer_id, internal_id, first_name, last_name and customer_group. Retrieve the order to read its addresses and the customer's other details.

The customer filters take different customer numbers. The customerId filter of List orders and Count orders takes the customer's internal_id. The customer's customer_id matches no orders there. List a customer's orders takes the customer's customer_id instead, and the customer's internal_id returns 404 with the message Customer Not Found. An order's customer section, or its customer_summary in the flat shape, shows both numbers.

Every address you send replaces the whole stored address. This holds when you create an order, and in Update an order, Update selected order fields and Update an order's addresses. A field you leave out of the address becomes "", so send every field of the address each time, not only the one you change. company_name is never stored and always reads "". An address without first_name returns 500 with the body {}. On an update, an address without country_code returns 500 with the message Cannot get property 'id' on null object. Update an order's addresses also accepts a country record with the country's id in place of country_code. Send first_name and country_code in every address.

  • A listing returns at most 20 orders per call and leaves out cancelled orders. A larger limit is capped at 20, and pagination.limit shows 20. Send page or offset to get the next orders. When you send both, offset wins. Cancelled orders are listed only when you send order_status=cancelled, and Count orders leaves them out too. A query parameter that is not on the List orders page, q included, is rejected with 400. To find orders by the customer's name or email address, use the customerName or search_text filter.
  • Payments and refunds change different totals. Record a payment on an order raises paid. Refund a payment lowers paid and raises refunded. It needs an Idempotency-Key header with a value you choose, and without it the call is rejected with 400. Sending the same value again returns the first refund again and refunds nothing more, so use a new value for each new refund. Refund an order raises refunded and leaves paid as it was.
  • Shipping lowers stock, and deleting the order does not restore it. Create a shipment lowers the stock of a product that tracks its stock, by the units shipped. Creating, paying, cancelling, completing and deleting an order change no stock. When you delete an order, the stock its shipments took is not given back.
